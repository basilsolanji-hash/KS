# Эксплуатация knitERP: среды, выпуск, резервные копии, мониторинг

## Среды

| Среда | Назначение | Данные | Мастер-ключ |
|---|---|---|---|
| Разработка | компьютер разработчика | демонстрационная организация | создаётся сам в `~/.kniterp/dev-master.key` |
| Тестовая | проверка выпуска перед рабочей, проверка восстановления копий | обезличенная копия или тестовые данные | свой, не как в рабочей |
| Рабочая | фабрика | реальные | в секретах сервера, копия в сейфе |

Каждая среда — своя база, свой мастер-ключ, свои учётные записи. Рабочие данные в тестовую среду попадают только
восстановлением копии для проверки, и после проверки база удаляется.

## Выпуск новой версии

1. CI зелёный на выпускаемом коммите (сборка, юнит- и интеграционные тесты на SQL Server). Из артефактов CI взять
   SQL-скрипт миграций `kniterp-migrations.sql`.
2. Собрать приложение: `dotnet publish src/KnitErp.Web -c Release -o publish`.
3. **Полная резервная копия рабочей базы** (`deploy/backup-kniterp.sql`, `Kind=FULL`) — точка отката.
4. Остановить приложение.
5. Обновить схему — один из способов:
   - `dotnet KnitErp.Web.dll migrate` (с рабочими настройками: строка подключения и мастер-ключ);
   - или администратор базы выполняет `kniterp-migrations.sql` (`sqlcmd -I …`), затем один раз `dotnet KnitErp.Web.dll migrate`
     для шифрования старых секретов 2FA.
6. Запустить новую версию. Рабочая среда не запустится, если миграции не применены, не задан мастер-ключ или соединение
   с базой не шифруется — причина будет в логе.
7. Проверить `GET /health` — ответ `Healthy`.
8. Короткая проверка: вход Владельцем с 2FA, «Остатки», «Проверка целостности», «Сверка».
9. Откат: остановить приложение, восстановить копию из шага 3, запустить предыдущую версию.

## Первый запуск на сервере фабрики

Рабочий сервер — VPS Beget (D08): пошаговая установка, резервные копии, обновление и восстановление — `docs/beget.md`
и скрипты `deploy/beget/`. Ниже — то же самое по шагам для любого сервера.

1. Создать мастер-ключ (`new-master-key`), положить в секреты сервера и копию — в сейф Владельца.
2. Применить миграции: `dotnet KnitErp.Web.dll migrate`.
3. Создать рабочую организацию (D59) — один раз:
   ```bash
   dotnet KnitErp.Web.dll create-organization \
     --name "<полное наименование>" --short-name "<краткое>" \
     --inn <ИНН> --kpp 770501001 --kpp-verified=yes \
     --owner-email <почта Владельца> --owner-name "<ФИО Владельца>" \
     --url https://<адрес программы>
   ```
   Команда печатает ссылку установки пароля Владельца (72 часа, один раз). Передать её Владельцу лично, не по почте
   в открытом виде. Повторный запуск с тем же ИНН ничего не создаёт. Ошибки параметров печатаются списком, код выхода 2.
4. Запустить приложение, проверить `/health`. Дальше — по `docs/pilot.md`.

## Настройки рабочей среды

| Настройка | Значение |
|---|---|
| `ASPNETCORE_ENVIRONMENT` | `Production` |
| `ConnectionStrings__KnitErp` | строка подключения с шифрованием (без `Encrypt=false`) |
| `Security__MasterKey` | мастер-ключ (`dotnet KnitErp.Web.dll new-master-key`) |
| `Security__PreviousMasterKeys` | прежние ключи после смены, через запятую |
| `Assistant__ApiKey` | необязательно: ключ Anthropic для ИИ-помощника |
| `Requisites__ApiKey` | необязательно: API-ключ DaData для заполнения реквизитов по ИНН (бесплатный тариф, dadata.ru → личный кабинет → «API-ключ») |
| `ASPNETCORE_URLS` | адрес и порт за обратным прокси |

Секреты — в переменных окружения службы или хранилище секретов, не в `appsettings.json`.

## Резервные копии (допущение D54, вопрос D17 открыт)

- Модель восстановления базы — `FULL`.
- Полная копия раз в сутки ночью, копия журнала транзакций каждые 15 минут: потеря данных при аварии — не больше 15 минут.
- Копии шифруются сертификатом TDE и проверяются `RESTORE VERIFYONLY` — `deploy/backup-kniterp.sql`.
- Хранение 35 дней; копии — на другом диске или сетевом хранилище и ещё одна копия вне здания (раз в неделю).
- Сертификат TDE, его пароль и мастер-ключ хранятся в сейфе **отдельно** от копий.

## Проверка восстановления

Раз в месяц: `deploy/restore-check.sql` разворачивает свежую копию в отдельную базу на тестовом сервере, проверяет
`DBCC CHECKDB` и выводит контрольные цифры. Затем на восстановленной базе запускается knitERP с рабочим мастер-ключом,
Владелец выполняет «Проверку целостности» и «Сверку». Результат записывается в журнал проверок (дата, копия, время
восстановления, итог). Цель — восстановление не дольше 4 часов (D54).

## Мониторинг

- `GET /health` (без входа): `Healthy` — база доступна и схема актуальна; `Degraded` — есть неприменённые миграции;
  `Unhealthy` — нет связи с базой. Опрашивать раз в минуту; при двух подряд не-`Healthy` — оповещение.
  На Beget это делает `deploy/beget/monitor.sh` вместе с проверкой диска, свежести копий и сертификата (`docs/beget.md`, раздел 7).
- Лог приложения: ошибки (`Error`), отказ в доступе, отказ запуска. Хранить 90 дней.
- «Журнал входов» (раздел «Доступ»): серии неудачных попыток с одного адреса и блокировки учётных записей.
- Раз в месяц после закрытия периода: «Сверка», «Проверка целостности», записать отпечаток.
- Свободное место на дисках базы и копий; срок действия сертификата HTTPS.

## Ответственные

| Что | Кто |
|---|---|
| Выпуск, настройки, мониторинг | администратор сервера |
| Резервные копии, проверка восстановления | администратор базы |
| Хранение мастер-ключа и сертификата TDE | Владелец |
| Сверка и проверка целостности после закрытия периода | Владелец или Аудитор |
